## Purpose
This file provides repository-specific guidance for coding agents working in this project.

## Repository summary
- Project type: single-module Android application
- Main module: `app`
- Language: Kotlin
- UI: Jetpack Compose + Material 3
- DI: Hilt
- Persistence: Room
- Async/state: Coroutines + Flow + `StateFlow`
- Navigation: `androidx.navigation3`
- Code generation: KSP

## Project structure
- `app/src/main/java/xyz/radenadri/starter/` — app source
- `app/src/main/java/xyz/radenadri/starter/data/` — repository and data modules
- `app/src/main/java/xyz/radenadri/starter/data/local/` — Room entities, DAO, database
- `app/src/main/java/xyz/radenadri/starter/ui/` — activity, navigation, screens, theme
- `app/src/test/` — local JVM unit tests
- `app/src/androidTest/` — instrumentation and Compose UI tests

## Coding style guidelines

### General principles
- Make the smallest correct change that fits the existing architecture.
- Preserve the current package structure and feature boundaries.
- Prefer consistency with surrounding code over introducing new patterns.
- Keep Android-specific logic in Android/UI layers and business/data concerns in data layers.

### Formatting
- Use standard Kotlin formatting with 4-space indentation.
- Keep trailing commas and wrapping consistent with the surrounding file.
- Prefer multiline formatting when constructor calls or composables become long.
- Do not introduce unrelated formatting-only edits in touched files.
- Preserve existing license headers if present in the file.

### Imports
- Follow the file’s existing import ordering and style.
- Prefer explicit imports over wildcard imports.
- Keep imports minimal; remove unused imports.
- Existing files generally use normal Kotlin/Android imports plus selective alias-free imports.
- Do not reorder imports aggressively unless the file is already being reformatted.

### Types
- Use explicit types for public APIs and important state surfaces.
- Type inference is acceptable for obvious local variables.
- Prefer immutable types and immutable exposures:
  - `val` over `var`
  - `Flow`/`StateFlow` exposures instead of mutable flow types in public APIs
- Model UI state with sealed interfaces/classes when there are multiple UI states.
- Keep domain/data contracts as interfaces where that pattern already exists, e.g. `TodoRepository`.

### Naming conventions
- Use `PascalCase` for classes, objects, composables, Room entities, and test classes.
- Use `camelCase` for functions, properties, parameters, and local variables.
- Use descriptive names that reflect behavior, not implementation detail.
- Test method names may use underscore-separated behavior style, e.g. `uiState_initiallyLoading`.
- Repository implementations should remain concrete and descriptive, e.g. `DefaultTodoRepository`.

### Compose conventions
- Keep composables small and focused.
- Hoist state upward where possible; prefer passing data and callbacks into composables.
- Avoid putting business logic directly in composables.
- Use theme values from Material/Compose rather than hard-coded UI constants when possible.
- Follow the existing pattern of wiring the screen from the Activity/navigation layer.

### ViewModel conventions
- Inject dependencies through the constructor.
- Use `@HiltViewModel` for DI-managed view models.
- Expose state as `StateFlow` or other immutable observable types.
- Use `viewModelScope` for asynchronous work.
- Keep ViewModels thin: orchestration/state mapping is fine; heavy persistence logic belongs in repositories/DAOs.

### Coroutines and Flow
- Prefer `Flow` transformations (`map`, `catch`, `stateIn`) over manual mutable state when appropriate.
- Handle stream errors explicitly when converting repository flows to UI state.
- Use `runTest` for coroutine-based unit tests.
- Avoid blocking calls in production code and tests.

### Error handling
- Do not swallow exceptions silently.
- Convert failures into explicit UI state when the UI needs to react.
- Keep error handling consistent with the existing architecture, e.g. `TodoUiState.Error`.
- Prefer meaningful propagation over broad `try/catch` blocks.
- Add logging only if there is already an established logging approach in the touched area.

### Dependency injection
- Use Hilt annotations and modules already present in the project.
- Prefer constructor injection for concrete classes.
- Add module bindings/providers only when constructor injection is insufficient.
- Keep test DI overrides in `androidTest` test modules.

### Room/data layer
- Keep Room schema-changing edits intentional; schema output is stored in `app/schemas/`.
- Repository methods should stay small and focused on mapping between DAO output and app-facing models.
- Prefer mapping close to the repository boundary.

### Testing guidelines
- Add or update tests for behavior changes whenever practical.
- Put pure JVM tests in `app/src/test`.
- Put Android/Compose UI tests in `app/src/androidTest`.
- Follow the existing fake-based testing style for repositories and view models.
- Keep tests deterministic and focused on user-visible behavior or contract behavior.

### File editing guidance
- Avoid renaming packages, classes, or top-level files unless required by the task.
- Avoid introducing new dependencies without a strong reason.
- If adding a new pattern or library, document why in the change summary.
- Keep generated outputs and manually maintained sources separate.

## Agent checklist before finishing
- Build or test the smallest relevant target.
- Run at least the most relevant unit test task when code changes affect logic.
- Run instrumentation tests only when UI/device behavior is affected and a device is available.
- Confirm no nonexistent rule files are referenced.
- Keep changes aligned with Kotlin, Compose, Hilt, Room, and Flow patterns already used here.
